# 11 · 采集/SD 写入的 CPU 负载分析与"15 秒分段"方案评估

> 背景：2026-11-15 观察到 MQTT/HTTPS（优先级 3）长时间没有任何进展，
> 怀疑采集任务的 SD 位翻转写占满 CPU。用户提出"每 15 秒一个录音片段、
> 保留 8 份、触发时保存 8 份片段+当前片段"的方案。本文给出定量分析与结论。
> 改采集/SD 相关代码或讨论缓存策略前先读本文。

---

## 1. 当前实现（不是"实时重写窗口"）

- PDM 麦克风经 I2S 采集，32 kHz、PCM16 单声道 = **64,000 B/s**；
- 音频按 4 KB 块追加写进 SD 的裸扇区环形区（LBA 2048 起），约 **16 次/秒**；
- "最近 N 秒窗口"只是环形区里的 **偏移 + 长度**，读取时按环回绕，
  **不存在每次触发重写整个窗口**的动作；
- 写入速率完全由音频数据率决定，与窗口大小无关。

## 2. 为什么"15 秒分段"不能降低负载

1. 要在任意时刻保留"最近 N 秒"，录音期间就必须以 64 KB/s 持续落盘；
   分段只是改变索引/边界，不改变字节数。
2. 若希望"每 15 秒才写一次 SD"，需要先在 RAM 里缓存 15 秒：
   15 × 64,000 = **960 KB**。ECW6700 的可用 SRAM 远小于此
   （当前应用 IRAM 已用约 60 KB），不可行。
3. 因此分段方案的 SD 写入量、CPU 占用与现在相同，只是代码更复杂、
   触发时还要拼接多段。**不采纳**，理由记录在此，避免重复讨论。

## 3. CPU 占用从哪来（定量）

- SD 是 GPIO 位翻转软件 SPI（`app_sdspi.c` 的 `bb_byte()`）：
  每 bit 两次 `sd_delay()`（8 次空循环）+ 4 次 GPIO 读写；
  实测有效吞吐约 100–180 KB/s 量级（取决于 CPU 频率与 GPIO 调用开销）。
- 64 KB/s 的音频意味着软件 SPI 占用约 **35%–60% 的 CPU**，再加上 I2S 解码
  与 4 KB 块拷贝，采集任务**大部分时间处于可运行状态**。
- FreeRTOS 中，可运行的高优先级任务会持续抢占低优先级任务：
  采集任务优先级 5 时，优先级 3 的网络任务（MQTT/上传）几乎拿不到时间片，
  表现为 TLS 握手 6 分钟无日志。

## 4. 缓解手段（按收益排序）

| 手段 | 收益 | 代价/风险 | 状态 |
|---|---|---|---|
| 网络任务优先级提到与采集同级（时间片轮转） | 直接解决饿死；TLS 约慢 2–3 倍但能完成 | 采集与 WPA 共享时间片 | **已实施**（`APP_TASK_NET_PRIO/UPLOAD_PRIO = 5`） |
| 采集直接存 16 kHz（32 KB/s） | SD 写入量与 CPU 占用减半 | 需在采集路径做 32k→16k 滤波（同一 `app_resample`），录音精度降为 16 kHz；上传/回放本来就是 16 kHz | 备选，优先级实测仍不足时再做 |
| 提高软件 SPI 时钟（减小 `sd_delay`） | 写入时间线性下降 | 受卡与时序裕量限制，需实测误码 | 备选 |
| 增大单次写入块（4 KB→8/16 KB） | 减少每块命令/CRC 开销，收益有限 | 主要影响首尾延迟 | 暂不需要 |

## 4.1 已实施：8 kHz 落盘（2026-11-15）

用户确认人声场景可接受电话带质量，已按"采样率 8 kHz"实施：

- PDM/I2S 采集仍为 32 kHz（麦克风时序不变）；
- `app_audio.c` 新增 **4 阶 Butterworth 低通（fc≈3.4 kHz）+ 4:1 抽取**，
  落盘 PCM16 8 kHz：SD 写入 **64 KB/s → 16 KB/s**，采集任务 CPU 占用约
  降至原来的 1/4 到 1/3；
- 上传：`app_upload.c` 用 `resampler_8to16`（2× 线性插值）升到服务端要求的
  **16 kHz WAV**，WAV 字节数与 SHA256 两遍处理保持一致（同样的分块与状态）；
- 回放：`app_playback.c` 的最近 N 秒回放走 8k→16k 插值；音效资产仍为 16 kHz；
- 环形区字节率变为 16,000 B/s，30 秒片段 = 480 KB；"最近 N 秒"换算自动跟随
  `APP_PCM_BYTES_PER_SEC`。

## 5. 决策

1. 先验证"网络任务同级优先级"是否足以让 MQTT/HTTPS 完成（本轮已改）。
2. 若 TLS 仍不可接受地慢，再实施"采集存 16 kHz"，并在本文更新实测数据。
3. 不采纳 15 秒分段方案，理由见第 2 节。

## 6. 验证方法

- 采集负载：`[app] status` 每 10 秒的 `total=` 增量应稳定 ≈ 640 KB；
- 网络进展：上电后看 `[mqtt] net up` → `[https] connected` → `[mqtt] time synced`
  → `[mqtt] connected` 的时间戳；
- 若 `[https] connected` 出现但耗时 > 2 分钟，考虑切到 16 kHz 采集。
